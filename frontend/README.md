# Frontend MVP «Кондитерская»

Русскоязычный React + TypeScript клиент для REST API из проектной документации. Это SPA без отдельного BFF: цены, доступность изделий, права и переходы статусов всегда определяет backend.

## Запуск

Нужен Node.js 20+ и npm 10+.

```powershell
Copy-Item .env.example .env.local
npm install
npm run dev
```

Откройте адрес, который выведет Vite (по умолчанию `http://localhost:5173`). Проверка production-сборки:

```powershell
npm run build
npm run preview
```

Проверить правила ввода и расчёт минимальной даты самовывоза:

```powershell
npm test
```

## Как пользоваться

1. Откройте **Каталог**, выберите изделие, вес и начинку, затем добавьте конфигурацию в корзину.
2. Войдите или зарегистрируйтесь как клиент. В **Корзине** перейдите к оформлению, заполните телефон и дату самовывоза, рассчитайте стоимость и подтвердите заказ.
3. В **Моих заказах** отслеживайте историю. Новый заказ можно отменить до подтверждения.
4. Сотрудник после входа видит **Очередь**: фильтрует заказы, последовательно меняет статусы или отменяет заказ с причиной.
5. Администратор использует раздел **Администрирование** для изделий, начинок и учётных записей сотрудников.

После обновления страницы потребуется войти снова: по требованиям MVP сессия не сохраняется в браузере.

## Переменные окружения

| Переменная | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `VITE_API_URL` | `/api/v1` | Базовый URL API. Для same-origin Docker/Nginx оставьте значение по умолчанию; для локального backend можно задать, например, `http://localhost:8000/api/v1`. |

Не добавляйте `.env.local` с секретами в Git. У фронтенда нет refresh-токена, клиентских ключей API или других секретов.

## Структура

```text
src/
  api/          fetch-клиент, контракты запросов, сессия в памяти
  components/   общий layout, состояния, пагинация, заказ, protected routes
  contexts/     Auth и Cart
  hooks/        переиспользуемые состояния асинхронных действий
  pages/        каталог, клиентские, staff и admin экраны
  types/        TypeScript-модели ответа API и ошибок
  utils/        форматирование Europe/Moscow и строгая валидация
```

## Поведение по контракту

- Access JWT хранится только в модуле памяти. После перезагрузки сессия отсутствует; при `401` токен очищается и пользователь попадает на страницу входа.
- Публичная регистрация вызывает только `POST /auth/register`; роль не передаётся браузером.
- Корзина объединяет одинаковые `product_id + filling_id + weight_g`, ограничивает 20 строк и 20 единиц конфигурации, но не хранит или не считает цены.
- Оформление сначала вызывает `POST /orders/quote`. `POST /orders` получает `Idempotency-Key`, созданный через `crypto.randomUUID()`. При сетевом сбое повторяется тот же ключ и идентичное тело; изменение корзины, контакта, даты или подтверждённой суммы создаёт новый ключ.
- `PRICE_CHANGED` показывает актуальную котировку из ответа и требует нового явного подтверждения. Конфликты версии, недоступность и недопустимые переходы поясняются на экране и предлагают обновить данные/изменить корзину.
- Денежные значения в UI отображаются только из серверных строк с двумя знаками; фронтенд не реализует формулу BR-02.

## Покрытие интерфейса

| Область | Реализовано |
| --- | --- |
| Публичная | каталог с поиском/пагинацией, карточка конфигурации, вход, регистрация |
| Клиент | корзина, серверная котировка, оформление, личный кабинет, детали и отмена `NEW` |
| Сотрудник | очередь с фильтрами, карточка, последовательные статусы BR-04, отмена с причиной и обработка `VERSION_CONFLICT` |
| Админ | создание и редактирование изделий/весов/связей, создание и редактирование начинок, создание/блокировка/разблокировка сотрудников |

Все поля имеют связанные подписи; ошибки текстовые; интерактивные элементы доступны с клавиатуры. Сетка и шапка перестраиваются для 360 px и 1280 px.

## Проверка по тест-плану

`npm run build` выполняет строгую TypeScript-проверку и production-сборку. Для сквозной проверки против развёрнутого backend используйте синтетические данные из раздела 5 документации и проверьте как минимум:

1. TC-08/TC-28: лимиты корзины, количества, телефона, комментария и даты.
2. TC-12/TC-13/TC-15: смена цены, недоступная конфигурация и повтор с тем же ключом.
3. TC-19/TC-20/TC-22/TC-23/TC-26: отмена клиента, очередь, причина отмены, конфликт версий и фильтры.
4. TC-24/TC-25: разграничение маршрутов и административные операции.
5. TC-27: клавиатурная навигация и страницы каталога/оформления на ширинах 360 и 1280 px.

## Согласованные предположения по `schema.d.ts`

Используется точный сгенерированный контракт. В нём отсутствует `GET /api/v1/admin/staff`, хотя он указан в текстовой таблице PDF, поэтому не придуман дополнительный запрос: экран создаёт сотрудника и выполняет блокировку/разблокировку по UUID, сохраняя последнюю успешно изменённую запись до перезагрузки. Также ответы `ProductDetail` и `FillingBrief` в схеме не содержат `is_active`; значение используется для create/update, а если backend не возвращает поле дополнительно, нельзя достоверно отобразить его текущий статус. Для полноценного серверного списка сотрудников и статусов доступности backend должен добавить эти поля/endpoint в OpenAPI.
